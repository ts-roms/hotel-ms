# ADR-0034: Load test, September 2026

- Status: Accepted, 2026-09-29
- Tooling: `scripts/load/` (see its README)

## Setup

- **Database:** `hotel_load`, filled through the public API:
  - 200 rooms at one property;
  - 18,169 bookings over 365 days (about 75% occupancy), one new guest each;
  - 120 guests in house, with charges.
  - Totals: 18k reservations and guests, 55k reservation nights, 38k audit rows and 19k
    outbox events.
- **API:** one process on a developer laptop (Windows, Postgres in Docker Desktop), with
  `DB_SLOW_QUERY_MS` logging.
- **Load:** a weighted mix of the busiest staff screens plus bookings and folio charges,
  with 1 user and with 40 users sending requests back to back.

**Caveat on local numbers.** On this machine, any database message of 16 KB or more costs
about 40 ms extra. The same 64 KB statement run inside the container takes under 1 ms, so
the cost is in Docker Desktop's port forwarding on Windows. Production (ECS to RDS) does not
have it. Timings of statements with large parameter lists are inflated locally, so query
cost was judged with `EXPLAIN ANALYZE` inside the container.

## Findings

1. **Foreign keys without indexes on booking tables.**
   - `reservation_rooms.reservation_id` had no index. Every screen that loads a booking's
     rooms scanned all reservation lines: detail, list, front desk, check-in and search.
   - `reservation_rooms.guest_id` and `reservations.booker_guest_id` had none either. Guest
     visibility and search follow both.
   - Also missing: `payments.folio_id`, `stays.room_id`, `housekeeping_tasks.room_id`, and
     room assignments by property and date.

   All of these are added in migration `20261006090000_load_test_indexes`.

2. **Housekeeping board.**
   - It loaded 200 rooms with four Prisma `include`s. Each sends two keys per room and costs
     Prisma CPU per row.
   - It now makes flat queries by property and joins the results in memory.
   - Single-user time went from 219 ms to 33 ms. Most of that gain is local (the port
     forwarding), but the query count and message size drop everywhere.
3. **Name search cannot use an index under row-level security.**
   - `ILIKE` (`texticlike`) is not leakproof. With RLS, PostgreSQL applies such filters only
     after the policy check, row by row, so no trigram index can serve them. Marking it
     leakproof needs a superuser, which RDS does not grant.
   - The existing combined-expression trigram index was never used, so it is dropped.
   - Measured in the container at 18k guests:
     - reservation search: 48 ms for a common name, 54 ms worst case;
     - guest search: up to 15 ms.
   - Both grow in step with the organization's guest count.
   - An index-backed option exists: search by "starts with" on a stored lowercase column
     with a btree index, since `>=` and `<` on text are leakproof. It changes what staff
     can find, so it is a product decision (below).
4. **The API is CPU-bound in one Node process.** With 40 users sending back to back:
   - it managed about 60 requests/s, with a median of 600–800 ms on every screen;
   - Postgres used about 2 cores, while the API sat at 86% of its single core;
   - the CPU profile: 38% Prisma client (query building and result mapping), 6.5%
     garbage collection;
   - each request spends about 8 database round trips on sign-in and tenant checks
     (session, identity, membership, grants, property, plus transaction setup) before its
     own queries.
5. **Bookings for the same room type and nights are serialized** by the inventory row lock
   (`FOR UPDATE` on `inventory_nights`), which prevents overbooking.
   - Generating 18k bookings with 16 in parallel ran at 33–43 bookings/s.
   - That is far above any real booking rate.
6. **Single-user timings after the fixes** (median):
   - availability 19 ms, quote 18 ms, folio 19 ms;
   - reservations list 30 ms, detail 21 ms;
   - front desk 57 ms, dashboard 68 ms;
   - calendar 145 ms: 14 days of arrivals and departures loaded with `include`s. Likely
     mostly the local artifact; re-measure in staging.

## Decisions

- Add the missing indexes (finding 1).
- Load the housekeeping board with flat queries (finding 2).
- Drop the unused trigram index (finding 3).
- Add the opt-in `DB_SLOW_QUERY_MS`. It logs slow statements by SQL text only, never
  parameter values. Leave it off by default; set it in staging and production (for example 200) to catch regressions.
- Keep the load scripts in the repository, and rerun them against staging, where timings
  are real.

## For the owner to decide

- **API sizing.**
  - Terraform gives each API task 512 CPU units (0.5 vCPU) and a fixed task count: 2 in
    production, 1 in staging.
  - Node uses one core, so each task is capped below what one core can serve.
  - Recommendation: 1 vCPU per API task (1024/2048), plus ECS service autoscaling on CPU
    (for example, target 60%, minimum 2 tasks).
  - Size the minimum after a staging load run. On this laptop, one process served about 60
    requests/s at saturation.
  - This costs more on Fargate.
- **Name search.** Keep "contains", which scans the organization's guests (fine up to
  roughly 100k guests), or switch to "starts with", which is index-backed at any size.
- **Per-request overhead.** Sign-in and tenant checks could be trimmed, for example by
  merging the session and identity reads, or caching grants keys in-process for a few
  seconds. This touches session revocation and isolation, so it needs its own review.
